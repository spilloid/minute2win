Why this exists

Reimaging a PC should take
one decision, not one afternoon.

You know the ritual. Find the USB stick. Wonder if it has the current image. Walk over. Mash F12. Click through Setup. Wait. Click some more. Walk back. Do it again for the next one.

minute2win replaces the ritual with a button. You decide at your desk, or on your phone, which machine gets a fresh Windows. The machine does the rest by itself: network boot, checks, countdown, partition, verified download, apply, reboot, first-boot script. You read the lap times afterwards.

How it works

Three moves.
One deliberate wipe.

You bring a licensed Windows image, WinPE from the Windows ADK, wimboot and iPXE. minute2win brings the console, the boot policy and the engine.

01

Arm

Enter a MAC address and a deployment profile in the console, or POST /api/armed. That is the whole decision. Arms expire on their own (two hours by default).

02

Boot

The machine network boots. minute2win’s built-in PXE (or your own iPXE) hands it WinPE and its manifest, and the arm is used up on the spot. Unarmed machines are ignored and boot their own disk.

03

Watch

The engine checks, counts down, partitions, downloads, verifies, applies and reboots, reporting every phase to the board. Windows Setup and a one-time first-boot script finish the job.

Arm MAC + profile → network boot → /boot/<mac> → arm consumed
  → wimboot loads WinPE + manifest → loader downloads the engine
  → check image and disk → 10-second abort countdown
  → partition → download + verify SHA-256 → apply Windows → bcdboot
  → copy logs → reboot → Windows Setup → first-boot bootstrap

The clock

The name is a promise
we measure, not assert.

The target: network boot to flashed Windows in about a minute, on an NVMe machine with a fast LAN. Every phase is timed, so you’ll see exactly where the seconds go. Here is the one run on record, and where the minute is hiding.

What you get

A deployment rig
you actually own.

For anyone who reimages machines again and again: homelabs, repair benches, classrooms, small IT shops. One binary instead of a deployment platform.

Console

One binary, one web page

A single Go server with the console and JSON API built in. Windows x64 (Authenticode-signed), Linux amd64/arm64 and an AppImage. Works offline.

Control

One arm, one deployment

An arm is used up the moment the machine asks for its boot script. The next network boot just boots Windows. No reimage loops.

Images

Pinned by SHA-256

A manifest names the image URL, its exact hash, the edition and the disk needs. A wrong or corrupted download never gets applied.

Boot

Built-in PXE, if you want it

Optional proxyDHCP and read-only TFTP that answer only armed machines, next to your normal router. Existing iPXE or USB boot works too.

Visibility

Every phase on the clock

Lap times live on the board. Logs and timing.json stay on the new disk under C:\Windows\Logs\minute2win.

Upkeep

Update without rebuilding WinPE

WinPE downloads the engine at boot. Change the scripts, and the next deployment uses them.

Safety

Destructive by design.
Guarded by design.

minute2win never asks “are you sure?” at the machine, because zero-touch means nobody is there to answer. The decision happens when you arm. Everything else makes the arm the only way in, and stops most setup mistakes before the disk is touched.

The one exception is the image itself: its SHA-256 can only be checked once it is downloaded, after partitioning. Try every new profile on a VM first. And no guard replaces checking which machine you arm.

Accepted risks and limitations →

Opt-in per boot

Only an armed MAC gets a deployment script, and serving it uses up the arm.

Arms are short-lived

Unused arms expire (two hours by default) and none survive a server restart.

Fails closed

If the server cannot durably record that an arm was used, it does not deploy.

Checks before the wipe

Manifest, image reachability and size, and disk capacity. A dead URL or a too-small disk leaves the machine as it was.

Picks the disk carefully

The lowest-numbered internal disk of at least 64 GB. Never USB or a file-backed virtual disk.

WinPE + UEFI only, with a countdown

The engine refuses to run anywhere else, and shows ten seconds any key can abort.

Set the token

Release 0.1.2 listens on every interface by default and the token is optional: without M2W_TOKEN, anyone who can reach the server, or any web page open in your browser, can arm a wipe. Set it, and pass -listen explicitly. The next release fixes the defaults: loopback first, no network listener without a token, cross-site arming refused.

Mind the static route

The static boot/minute2win.ipxe deploys on every boot that reaches it. Use it only behind a per-boot opt-in; prefer server arms.

Just want to see the console?

Run the server on loopback with a token. Nothing else on your network can reach it, so nothing can be armed for real.

# Windows PowerShell, in the extracted release folder
$env:M2W_TOKEN = 'replace-with-a-long-random-token'
.\minute2win-server.exe -listen 127.0.0.1:8080

# Linux
export M2W_TOKEN='replace-with-a-long-random-token'
./minute2win-server -listen 127.0.0.1:8080 -open=false

Before you arm anything

Straight answers.

Is it really one minute?

Not yet shown. About a minute on NVMe with a fast LAN is the design target and the reason every phase is timed. The only recorded run, a small VM pulling a large image from a remote host, took about six minutes, almost all of it moving bytes. The project will not claim a speed it has not measured, and the board will tell you yours.

Could it wipe the wrong machine?

It deploys only to a MAC address you armed, once, and only from WinPE on UEFI. On that machine it picks the lowest-numbered internal disk of at least the profile’s minimum size, never USB. If the machine has several internal disks, check which one that is first. Arming the wrong MAC wipes the wrong machine: the guards cannot know your intent.

Do I need a special network, or to replace my router’s DHCP?

No. The built-in PXE is proxyDHCP: your router keeps handing out addresses, and minute2win only adds “boot this file” for armed machines. Everything else on the network never notices it.

Does it need a cloud service or an agent on the machine?

No. The server runs on a Windows or Linux host on your network. Targets need nothing installed: they network boot, and WinPE fetches the engine.

Does it include Windows?

No. You supply a licensed Windows image, WinPE built with the Windows ADK, wimboot and iPXE. Windows licensing stays your responsibility.

Domain join? Entra? Secure Boot? Real hardware?

Joins are not implemented yet; enroll machines with your existing process afterwards. Secure Boot and physical firmware are unverified: the full chain has run on a virtual UEFI machine, and physical machines are the next milestone. See Status before deploying.
